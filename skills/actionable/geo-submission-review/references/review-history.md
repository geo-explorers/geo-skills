# Curator review history

This is a supplementary Notion record for every completed substantive review across spaces, bounty types and manual/scheduled modes. Geo datasets remain the recipient feedback destination. A log entry preserves what the review said when given, even when the Geo page is later updated. Report publication is not proof of Discord delivery, editor approval, execution or payment.

## Destination and identity

Use `notion-operations` and one connected editor identity for retrieval, creation and same-identity verification. Resolve the editor's existing `curatorReviewLog` runtime configuration outside the installed skill; it contains `required`, `databaseUrl`, `dataSourceId`, unfiltered `lookupViewUrl` and applicable authorization. Do not confuse this with `reviewHistory`, the runner's old proposal-seed map. Mohammed's active configuration also applies to his specified-submission and other-space reviews; resolve that existing deployment configuration rather than creating a separate database per space. Other editors must configure their own authorized destination. Do not copy another editor's access or approvals.

The established destination is a **Curator review history** database under the editor's Datasets design hub. Search and inspect an existing matching database before creating one. Read its live schema; use its actual collection/data-source ID for row writes. Do not use PEOPLE for curators without verified Notion accounts, or create separate curator/bounty databases just to satisfy a relation preference. Stable Geo curator IDs plus names allow matching without confusing namesakes.

Required properties for the supplied payload helper:

| Property | Type | Meaning |
|---|---|---|
| Review | Title | Curator, bounty or task, UTC review date |
| Review date | Date | Actual publication date/time of this feedback, not the scan time or invented delivery date |
| Curator | Text | Verified display name |
| Curator ID | Text | Verified stable Geo identity |
| Space | Text | Submission space |
| Submission | Text | All constituent proposal/submission links |
| Bounty | Text | Actual bounty name, or “No formal bounty” |
| Bounty URL | URL | Verified bounty link; empty when none exists |
| Geo report | URL | Verified recipient report |
| Outcome | Select | Meets requirements / Needs correction / Does not meet requirements; these are review assessments |
| Error types | Text | Every distinct verified category; no issues is recorded truthfully |
| Review key | Text | Stable identity for deduplication |
| Editor feedback | Rich text | Human editor notes about agent mistakes; omit from every agent create/update property payload |

Adapt to a compatible existing schema rather than duplicating it; document any mapping. The entry body uses the fixed [Notion report layout](notion-review.md#required-page-structure): three concise single-line bullets labelled **Accepted**, **Needs correction**, **Next steps**; the full seven-column table matching Geo; then one final **Submissions reviewed** toggle containing linked bullets. Do not add a Published review preamble, Submission/Feedback as published headings, previous-review paragraph or audit appendix. The Geo report URL, dates, identity, bounty, review key and outcome stay in properties. Preserve previous-review links and the original published snapshot/hash in the durable log journal, without extra body sections. A live Geo URL alone does not preserve historical feedback. Keep editor-only points, caps, private notes, voting controls and raw review JSON out of the shared log.

Provide a newest-first **Latest reviews** view and a **By curator** view, plus an unfiltered **All review records** lookup view exposing stable curator IDs and Review key. **Editor feedback** is visible in all three. Reuse the existing database, property and views; do not create duplicates. Views do not make records private. Do not change sharing permissions or migrate existing databases as part of routine logging. Editor feedback belongs to the human editor: read it as context about agent mistakes, verify relevant observations against evidence, and never clear, rewrite, summarize or copy it into generated feedback. Omit the property entirely even when empty. A content update must not resend stale metadata; verify the human field is preserved afterward.

## Before and after a review

1. Read relevant prior rows by stable curator ID, submission/case and bounty, with pagination or a complete filtered query. Use prior feedback to distinguish corrected, repeated and new issues. Do not turn an old allegation into a current finding without fresh evidence. Missing access means history unknown, not empty.
2. Complete material decisions, publish the Geo report and verify the report and every finding. Capture the recipient-facing content actually published and its readback evidence. The evidence-check date is not automatically the date feedback was given. Do not describe a draft as given feedback.
3. Prepare one history entry per curator/bounty case and substantive review revision, including reviews with no errors, rejected work and tasks without a bounty. Use `historyKey(case)` from `scripts/review-history.mjs`: stable case ID plus `reviewContentHash(case)`. It ignores scan/retrieval timestamps, renderer changes and private scoring. A substantive new assessment, changed submission or changed recipient feedback gets a new entry; an unchanged rerun does not. The previous snapshot remains intact.
4. Fetch the configured lookup view and confirm its source and absence of filters. Paginate its active and archived records to completion and compare Review key exactly before creation, even if local state says it is new. A complete exact lookup must establish zero matches; unknown or truncated results do not. If one exists, fetch and verify its properties and feedback snapshot, then adopt it. Multiple matches are a reconciliation task; do not delete them or add another. Serialize logging under durable run ownership; the text key is not a Notion uniqueness constraint. Concurrent hosts must coordinate ownership and reconcile conflicts rather than claiming exactly-once delivery.
5. Persist the intended key, original published snapshot/hash, rendered body/hash, publication date, previous review URL when applicable, destination and evidence before writing, with status `unknown`. Create under the live data source. Reconcile asynchronous results and read back every required property and the feedback content using the same identity. Verify the three single-line bullets, every complete table row/citation and final collapsed list; tolerate only documented Notion escaping/link normalization. Record the verified history URL, readback time and evidence in durable case state. Only then is logging complete.
6. If a call times out or fails, query/fetch the intended key and inspect its journal before retrying. Do not blindly create another page. A positive, evidenced `verified_not_created` reconciliation permits another attempt; missing search results or a missing local receipt alone do not. Preserve the original date and snapshot while resolving an older pending log after a new review revision.
7. Report logging success in the existing completed-actions section of the private editor handoff. A log failure goes in existing blockers/required action with the Geo publication shown as successful. Leave only the Notion log pending; do not republish the report, repeat votes/payments or send messages to recover logging. Retry pending logs on later runs under the original scope, without re-reviewing unchanged work.

Logging is required even when a scheduled scan cannot access Discord. It must not open Discord to collect process answers or verify message sending. Record a curator's explanation only when actually received through an authorized task; preserve their wording and provenance, and never infer the cause. A curator's explanation is not required to complete an evidence-backed review. If no error was found, do not manufacture a process question.

## Packaged offline helpers

`scripts/review-history.mjs INPUT_JSON OUT_JSON` prepares a Notion create payload and active/archived view lookup requests for exact-key comparison; it does not write Notion. Input contains `case`, verified `configuration`, actual `publishedAt`, the original `feedbackSnapshot`, `snapshotReviewContentHash`, `publicationEvidence` and optional verified `curatorId`/`submissionUrls`. For concise authored introductions supply `notionSummary:{accepted,needsCorrection,nextSteps}`; otherwise the renderer supplies truthful short defaults. It prefixes Accepted with “Review recommendation:” and rejects workflow-action claims. Supply captured `items:{[itemId]:{name,proposalUrl}}` when item names/URLs are absent from findings and coverage. Names can fall back to stable IDs, but links must be captured rather than guessed. `scripts/notion-report.mjs` renders the fixed body and validates its layout. Full finding values and stable finding links come from the same case as Geo; keep the publication snapshot as independent evidence and compare against its readback before writing. `snapshotHash` still identifies that original snapshot; `bodyHash` identifies its Notion presentation. Presentation changes do not alter `historyKey` or queue new historical entries. Review readiness and current Geo receipt are checked. Historical uncategorized feedback is labeled as historical, not retrospectively rewritten. An existing verified local log returns `already_logged`; unknown/failed logs return `reconciliation_needed` without a fresh-create payload.

An explicitly requested **single-page format update** can use the exported `prepareHistoryFormatUpdate(case,input,configuration,existing)`. This is never invoked by repeat scans or merely by upgrading the skill. Set `input.allowFormatUpdate:true` only within the editor's requested scope. Fetch `existing:{id,dataSourceId,content,properties,readbackAt,evidence,lookup:{complete,matchCount,evidence},hasInlineComments}`. Require the exact Review key/data source and one complete active/archived lookup match; reconcile duplicates or uncertain writes first. The helper returns only an exact-match `update_content` command, no create fallback and no property payload, preserving Editor feedback and all metadata. Protect inline comments before replacing managed blocks; do not include unrelated human body content in the replacement. Fetch again after an authorized update, verify full evidence and human properties, and retain the original date/key/snapshot journal. This release does not authorize historical rewrites or backfills.

The agent uses the connected Notion tools for exact lookup, creation and readback, following their current schemas. This deployment’s connector permits view-mode querying; filtered rows mode is rejected. Use the configured unfiltered lookup view and paginate active/archived rows. On another host, an exact rows/SQL filter may be used only if the live tool schema and access permit it; never relax duplicate checks to work around an unavailable query. Record results with:

```bash
node scripts/review.mjs history-receipt --history RECEIPT_JSON --state STATE --out RUN
```

Receipt: `{caseId,fingerprint,key,snapshotHash,publishedAt,status,recordedAt,evidence:[...]}`. Verified records additionally have `url` and `readbackAt`; a retry reconciliation uses `status:"not_created"`, `outcome:"verified_not_created"` and `reconciledAt`. Preserve the journaled key/date/snapshot. This command only records local evidence; it cannot establish a Notion success on its own. Other environments can persist an equivalent durable record with the same checks if the runner is unavailable, stating that limitation.

Start prospective logging when this requirement is configured. Do not bulk backfill old reviews or invent their dates/sending evidence. Historical backfill needs a defined, verified scope; do not describe the database as containing all past reviews until that work is completed.
