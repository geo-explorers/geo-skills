# Discovery and recurring review

## Runtime and durable configuration

Use `scripts/review.mjs` with Node.js (Node 20+), fetch and the installed `@geoprotocol/grc-20` decoder. Stage 0 finds the decoder through `GEO_CM_DIR` when this skill is deployed separately from content-management. No private key is needed for intake. Use the workspace's configured public editor/injector IDs. Keep configuration, state, cache and dated runs outside the installed skill. Do not derive a first-run checkpoint from an old brief.

The JSON configuration contains `editorSpaceId`, optional `injectorSpaceId`, shared `cacheDir`, `concurrency` (default 8), `intakeTimeoutMs`, and `spaces`. The optional deployment setting `curatorReviewLog` holds the required Notion database URL, data-source ID and authorization; see [review-history.md](review-history.md). This differs from the legacy proposal seed map `reviewHistory`. Do not put workspace-specific destinations into this portable skill. Each space has `enabled`, `firstSince`, `bountyProfiles` by full bounty ID, evidence-backed `dispositions` for verified non-bounty work, explicit `assignments` where needed and verified `editOrder` for multi-payload proposals. Supported keys are crypto, ai, health, world-affairs and us-politics. Scripts carry the main/datasets IDs. A profile is `{family:"routine",kind:"news|x|blog|fact-check|organize-claims"}` or `{family:"bespoke",singleDeliverable:true}`. Distinct deliverables need an explicit `caseKey`. Profiles classify work; they do not replace full requirements.

`reviewHistory` maps exact proposal IDs to `{evidence:[...],...}` with actual review/decision receipts. Seeds never mean approved or paid unless the receipt says so. Untagged assignments require recorded evidence and item IDs; mixed bounties require explicit disjoint item partitions. Do not guess from title similarity. Routine case keys are Lagos submission dates; revisions to the same existing items follow their earlier case. A mix of repairs and new items needs explicit partitioning. Bespoke cases span proposals/days for the same deliverable.

Run commands from the installed skill directory, with absolute paths for configuration/state/output:

```bash
node scripts/review.mjs preflight --config CONFIG --state STATE --out RUN
node scripts/review.mjs scan --space crypto --config CONFIG --state STATE --out RUN
node scripts/review.mjs evidence --state STATE --out EVIDENCE
node scripts/review.mjs record --review REVIEWS_JSON --state STATE --out RECEIPT
node scripts/review.mjs reports --state STATE --out DRAFTS
```

`scan` uses an explicit first cutoff, then the saved discovery cutoff with 60-second overlap. Both latest-300 feeds must cross the cutoff; incomplete discovery fails closed. Saved `proposalHistory` is the tested cursor fallback for overflow/bootstrap. It is not automatically substituted by the fast scanner. Do not attempt recovery by changing only `--until` on the same saturated latest feed. Keep failed retrieval receipts and exact blocker; no-new-work is a complete empty result, not a failed fetch.

Stage 0 saves a full proposal inventory and skipped-editor/injector reasons, lossless `raw-edits.json`, actions, names and compact previews. Only full raw values drive reviews. Full-field reads retain typed values, ownership and count checks. Cached binaries are decoded/validated before reuse. Specifications are fetched once per distinct bounty and include ordered blocks, complete text, snapshot hash and linked-criteria candidates. Linked Geo criteria page/block shells are snapshotted and included in the specification fingerprint; their table rows/query results and external documents still require explicit retrieval and coverage checks. Resolve relevant linked criteria before assessing the case, and record effective scope/date. Current changed requirements need applicability evidence before being imposed retrospectively.

## Review the queue

Read `case-summary.json`, `review-queue.json` and the persisted identification queue. A complete intake is not a completed review. `evidence` writes each case's ordered submitted operation history and projection. Unchanged fields require a captured baseline; today's live graph is not automatically the submission-time baseline. Preserve pending/deleted/unindexed/error distinctions. Inspect submitted IDs before name-search matches; empty stubs cannot replace the actual payload.

Use the review workflow in SKILL.md, [bounty-profiles.md](bounty-profiles.md), and the News reference as applicable. Every scoped item and applicable requirement needs an outcome and evidence or a precise gap. Reviews use `meets_requirements`, `needs_correction`, `does_not_meet_requirements` or `unresolved`; these are agent assessments, not votes or editor decisions. `checkedAt` is the actual evidence cutoff. Include one specific feedback row per distinct verified error type, without a five-row cap; retain all assessed items, repeated occurrences and unresolved checks internally.

New reviews use `feedbackPolicy:"error_types_v1"` and `verifiedErrorKinds:[...]`, naming each verified error type once. Each finding also has matching `errorKind`, neutral `processQuestion`, concrete `prevention`, `repairEligible` and, only when useful, `repairRequest`. A repair is useful when it changes eligibility or corrects otherwise eligible work; independently ineligible items receive future guidance instead. Every named type must have exactly one supported example. The CLI enforces this contract on newly recorded reviews; existing historical reviews stay readable and are not reopened merely to adopt the new format.

For completed multi-item news, X and blog cases, write `recipientSummary:{acceptance,rejection,feedback}` as three concise single-paragraph fields, following [geo-delivery.md](geo-delivery.md#routine-three-bullet-introduction). The feedback field briefly names the applicable checks, asks how the verified issues slipped through, and gives useful correction/prevention guidance; adapt the approved example to the actual bounty and space. This is recipient copy, not the private editor tally. The introductory Text block contains only those three bullets; the complete table and finding pages stay beneath it. A renderer-only change does not trigger publication or another Notion history entry for unchanged reviews.

A review JSON has `caseId`, current `fingerprint`, `outcome`, `checkedAt`, `coverage:[{itemId,outcome,evidence,note}]`, `requirements:[{criterion,outcome,evidence}]`, and `findings`. Each finding has `itemId`, optional verified `itemUrl`, full `original`, `originalRef:{proposalId,entityId,propertyId,cid?,opIndex?}`, exact `excerpt`, `issue`, `citations:[{url,locator,retrievedAt}]`, and `evidenceDetail`. Missing-field rows use `missingField:true`, `missingRequirement` and no invented excerpt. The recorder rejects stale fingerprints, omitted items, shortened originals and nonverbatim excerpts. It verifies provenance, not factual accuracy; sources must still be independently read.

Record publication receipts separately through `delivery --delivery FILE`; a verified receipt needs current fingerprint, report ID, URL and readback time. Failed/unknown updates retain earlier delivery history. Record explicit human decisions through `decision --decision FILE`, with stable `id`, `caseId`, `kind`, `recordedAt`, and authorization `evidence`. Preserve previous assessments, comments and editor close-outs. A later discretionary payout/close-out does not erase QA, and old QA must not revive an unpaid hold. `review_unresolved` cases remain in state; revisit at a configured retry interval or when evidence changes rather than researching unchanged inaccessible evidence twice daily.

## Final-report completion gate

Record `decisionGaps:[...]` for remaining material bounty requirements that prevent a decision. `reviewReadiness(case)` checks the current assessment, all scoped item decisions and these blockers. A correction recommendation is complete when the specific defect is supported; additional checks that cannot change that recommendation are internal audit limits. For routine multi-item news/X/blog cases, independent `selection` decides eligibility; general copy-check uncertainty must not override resolved event selection.

`reports` prepares final-review drafts only for ready cases. It lists incomplete cases under `investigationNeeded`, preserving prior drafts and receipts without presenting them as current final reports. Resolve those cases with primary or accessible authoritative evidence, then record the revision and rerun. `buildReportOps` repeats the completion check before preparing publication operations; a changed label or older draft cannot bypass it. Never fabricate a decision to empty the queue. An externally blocked case produces a separate work-in-progress update, not a final submission report. Final reports keep every curator in scope, including bespoke cases without routine point scoring.

## State, recovery and delivery

`state.json` schema 1 stores per-space discovery cutoff, pending identification, proposals with raw snapshots/items/prior receipts, cases with stable identity, specification, fingerprints, reviews/revisions, editor decisions, and separate delivery status. Locks are exclusive; investigate ownership before removing a stale lock. State replacement is atomic. Discovery advances only after durable capture; unresolved review/delivery work remains separate. Captured cases and ambiguous work are reconsidered on subsequent scans without downloading immutable CIDs again. Identical captured proposals retain established case membership and historical review/decision/delivery state. Missing current profiles/specs and changed specifications appear in `dependencyWarnings`, not as newly unidentified submissions. Check actual criterion changes and applicability before revising a historical case. Mutated captured payloads still fail closed for explicit version reconciliation; they cannot silently overwrite approved snapshots. Fatal runs do not replace a successful state.

`reports` generates Markdown and JSON drafts with deterministic report page IDs and the corresponding datasets target. Identical cases map to the same report; an explicitly adopted existing report ID is retained. Unchanged verified drafts are listed separately in the receipt and retain verified delivery status. `historyLoggingPending` exposes missing logs for newly authored category-contract reviews and unknown/failed logging attempts, including older revisions. Retry that logging work independently; legacy reviews are not automatically backfilled. A recipient-content hash ignores renderer changes, private scoring, evidence-check timestamps and citation retrieval timestamps; an identical recorded review also preserves delivery. Legacy receipts for the exact case fingerprint retain their verified state. An unpublished prepared draft remains actionable on rerun. Changed drafts retain prior delivery history. Submitted, unknown and failed deliveries are listed under `reconciliationNeeded` and cannot yield fresh create operations, including after a new case revision. Before broadcasting, durably record the publication intent and mark delivery `unknown` with its exact fingerprint and journal evidence; record `submitted` once its proposal/transaction is known. Recover by reading the existing journal, transaction and indexed report through geo-publish. Record `verified` only after readback. If reconciliation positively proves no write was submitted, `delivery` accepts `status:"retryable"` with `receipt.outcome:"verified_not_submitted"`, a parseable `receipt.reconciledAt`, and concrete evidence; this returns it to draft preparation. A timeout or missing indexed page alone is not such proof. A pending old fingerprint can be reconciled after a case revision without falsely marking the new revision delivered. The six fields are **Entity | Full original statement | Exact excerpt under review | Issue | Citations for quality checks | Relevant quote or evidence detail**. Full originals survive; no supported finding produces a truthful scope statement, not manufactured problems. Read [geo-delivery.md](geo-delivery.md) for authorized publication and readback. Report draft creation does not complete Geo delivery.

## Scheduled-run defaults

A request to run `geo-submission-review` for a named space **in scheduled-review mode** invokes this section. Keep the scheduler prompt short; maintain the shared behavior here. Timing and timezone belong to the scheduler, not to a copied review algorithm. These instructions do not activate a schedule.

1. **Use the shared repository workflow.** Editors use the content-management repository and its installed skills. This skill orchestrates, `geo-query` retrieves the graph and `geo-publish` publishes reports with its safeguards. Only the target space changes; do not require an editor-authored review-setup document or Mohammed-specific paths, private history or credentials. Resolve the installed repository, existing configured editor identity, paired spaces, applicable requirements/rules and durable space-scoped state/output locations. Validate access and identity rather than guessing. Keep secrets out of outputs. Never copy one editor’s approvals or assignments to another editor.
2. **Sweep both spaces completely.** Include the named main space **and its paired datasets space**, even if the prompt names only the main space. Verify both live identities and required coverage; group the curator’s related proposals across both without double-counting items. Resume the last complete durable checkpoint, retain unfinished cases and check existing Geo reports before creating one, including on a fresh host. Use an explicit recorded initial cutoff when no checkpoint exists; do not invent a cutoff or treat an old brief as progress. Report any missing bootstrap setting precisely. Reconcile cross-editor reports before publication; local locks alone cannot prevent duplicates across hosts.
3. **Discover from Geo; do not access Discord.** Do not open, read or search Discord channels, DMs or inbox connectors during this mode, even when available. Identify submissions through Geo metadata, full submitted operations, explicit bounty relations and previously verified mappings that already belong to this editor’s state. Do not obtain new mapping evidence from Discord. If curator, bounty or submission scope cannot be established, preserve exact proposal links in `needs-identification`, state the missing information and continue independent cases. Missing identification is not rejection or permission to omit a proposal. This restriction is specific to scheduled-review mode; an explicitly requested manual Discord investigation is a different task.
4. **Review changes and retain history.** Review new or materially changed work and due investigations against the complete applicable criteria. Preserve prior reviews, comments, editor decisions, approvals and award receipts. Do not re-review or republish unchanged completed cases just because a schedule fires or a renderer changes. Do not demote a verified historical case because a current dependency fails; preserve its evidence and report the current blocker. Complete material item decisions before final delivery; blocked research stays in the private investigation queue with its next step. Do not repair workflow code/config silently during a routine run.
5. **Deliver reports, log reviews and draft feedback.** Publish completed new or substantively revised reports and full linked findings to the verified matching datasets space under the editor’s applicable report authorization. Read back the report and open every finding. Log each completed substantive review in the configured Notion review-history database through the connected editor identity; follow [review-history.md](review-history.md), reconcile unknown logs before retrying and record its verified URL or precise logging blocker. Read prior curator history without accessing Discord. Reconcile unknown writes before retrying; preserve comments and human decisions. Draft short, kind Discord replies with verified report links without accessing Discord. Distinguish passing work from failing work and identify repairs, using the actual recommendation/decision stage so the curator need not redo accepted work. Show the exact accepted-story/item count with its specific rundown; keep scoring, points and cap calculations private to the editor. Follow the existing delivery and feedback references; do not invent a published URL or final award.
6. **Preserve exact authorization boundaries.** Publication of review reports does not authorize votes, separate execution, payments or message sending. Present concrete proposed votes and execution consequences in the editor handoff; wait for approval of unapproved actions without keeping the background run open. Existing recorded approval for the exact unchanged votes or separate execution remains valid: carry out those eligible approved actions through the prescribed safeguards and verify receipts without asking again. Separate execution must be explicitly covered; payments and sending need their own concrete authorization and separate workflow; this scheduled scan only drafts messages and calculates supported points. Reconcile prior outcomes and never repeat a completed action. A scheduled trigger, elapsed time or approval of another batch grants no new authority. Do not repeatedly notify about an unchanged pending approval.
7. **Persist and hand off every run.** Use shared durable state/cache and exclusive run ownership; process requested spaces serially with bounded intake concurrency. Save progress between cases and respect the configured run budget/retry policy; leave inaccessible work queued. Generate the fixed private editor report for completed, empty, partial and failed runs, preserving all template sections. Distinguish failed intake from no new submissions. Record the skill version/commit, configuration provenance, coverage and receipts. Notify only for new actionable results, a material change, completion of an approved action, or a failure/decision requiring attention. Save unchanged reports quietly. A configured schedule or successful component test is not proof of successful unattended runs.

**Current implementation boundary (v0.7.2):** these are agent instructions, not a claim that the runner implements every scheduling safeguard. The packaged CLI still requires explicit config/state/output arguments. Automatic fresh-environment initialization, general comment-preserving update verification, full-workflow ownership, enforced retry/run budgets and actual unattended access remain separate checks. Historical replay, complete description-only specs and publication reconciliation now have regression coverage; this does not prove every unattended path. Use existing validated configuration for supervised runs; surface an unmet prerequisite without inventing success. A shared first-run lookback is not yet adopted by this skill. Do not activate an unattended routine until the relevant checks pass.

## Editor-only multi-item tally and points

For routine news, X and blog cases with multiple items, give the editor a separate summary of how many distinct items **pass the review**, **fail**, and which items are in each group. Until an editor decision is recorded, label these as recommended acceptance/rejection; do not describe a review recommendation as an executed vote or payout. Repeated proposals or dual residency of one entity do not earn multiple item credits. Count all distinct items, independently of the one-example-per-error-type recipient feedback.

Record each coverage row’s independent `selection:{outcome:"qualifies|does_not_qualify|unresolved",evidence:[...]}`. Do not infer credit from a general `needs_correction` outcome: the applicable Crypto injector rule separates copy feedback from qualifying event selection. Unknown selection stays in the internal investigation queue and prevents a final tally or report. Resolve it before final reporting. Preserve actual editor decisions separately.

Load the workspace’s current canonical point rules (Geo workspace: `tooling/bounty-pipeline/POINT-SYSTEM.md`) and any applicable bounty override; retain effective dates and rule provenance. Do not apply one space/category’s policy to another automatically. Record `scoring:{rate,ruleSource,weekly:{limit,priorPoints,period,evidence:[...]},monthly:{limit,priorPoints,period,evidence:[...]}}`. Use the relevant curator/category/space’s prior credited points across all batches. Prior credit is net of this case, so a repeated review does not consume the cap twice. A missing ledger is unknown, not zero. Confirm the period boundaries from the applicable ledger; UTC display does not change scoring weeks or internal case grouping.

Calculate accepted distinct items × applicable rate, then apply remaining weekly and monthly headroom. Show the calculation, pre-cap points, verified cap adjustments and resulting points. If cap usage or the rate is unknown, give the supported subtotal and the exact pending check; do not invent a final award. Bespoke bounties use their own award rubric and do not automatically receive per-entity routine rates. Rankings bonuses and discretionary editor awards stay separate.

`scripts/review-core.mjs` exports `editorSummary(case)` and `editorSummaryMarkdown(summary)`. The `reports` command writes separate `<caseId>.editor.json` and `<caseId>.editor.md` files for eligible cases. The scoring calculation and cap/ledger details are for the editor only: never add them to recipient Markdown, Geo report operations, shared Notion pages or Discord replies. Public acceptance counts and the classified Notion lists are permitted: linked replies should distinguish accepted or recommended-accepted work from rejected or recommended-rejected work, using the actual confirmed decision stage. Reporting recommended points does not authorize paying them.

## Finish every run with the standard editor report

Follow [editor-run-report.md](editor-run-report.md) after the overall agent run, not after every internal command. `review.mjs summary --summary RUN_SUMMARY_JSON --state STATE --out RUN` renders the bundled template; the standalone renderer needs only Node built-ins and works without Geo SDK access. Save a report for empty, partial and failed runs too. Include identification and investigation work alongside completed cases; use unknown counts when intake failed. Record publication failures explicitly. Persist no-change reports without routine notifications. This step is mandatory before handing control back to the editor, and again after approved actions.
