# Datasets-space report delivery

Every submission review targets the matching Geo datasets space: discovery, recurring scans and individually supplied submissions, with or without a formal bounty. Existing Notion mirrors are supporting inputs, not delivery destinations. Use a different destination only when explicitly requested for the current review. `preflight` checks the configured public editor's membership; actual signer capability and current proposal rules must also be checked through geo-publish before a write. Membership alone does not prove that this runtime can publish. Verify the live destination ID, name and actual signer authority; never select between same-name spaces using a name or stored ID alone. Prefer the supplied submission’s verified datasets residency where applicable. Disabled recurring scans still need a first-run checkpoint, full criteria and retrieval/access verification before activation; a separately requested individual review does not activate scanning.

Use geo-publish for schema/typed-create/semantic-duplicate checks, dry-run operations, applicable human authorization and readback. The default standing authorization from Mohammed covers completed recipient review reports and their findings in the corresponding datasets spaces, including report-owned updates that preserve comments and decisions. Record its scope and source in the dated delivery receipt; do not ask for duplicate authorization within that scope. A different destination, a change to shared schema or unrelated content needs its own authorization. Read ontology-advisor when choosing a report model. Inspect existing report pages and the target-space schema first. A personal-space Review finding prototype is precedent, not proof that its custom types/properties are available in each destination. Prefer an existing compatible model; do not recreate identical types or findings.

Use the deterministic `pageId` in the report draft plus `caseId`, bounty and constituent proposal IDs as matching evidence. Before first creation, search existing reports by these identifiers and exact/normalized title. A compatible legacy report may need adoption rather than creation. Before updates, read the existing page, comments, human decisions and currently indexed operations. Preserve user material; propose only changed report-owned fields. Local deterministic IDs alone do not prevent duplicates against a pre-existing report under a different ID.

Keep the submission title in the page name only, with no repeated body heading. Use plain, kind status language and record a readable UTC date in the page name/metadata; non-routine reports may show it in the body. Comparisons that need hours use explicit UTC timestamps. Precise timestamps and assessment codes stay in the internal record. Tell the reader: “Open each review in the table below to see the full details, including the original statement, the issue and supporting sources.” Open each linked finding during delivery verification and check that its complete content and evidence are readable. Do not imply acceptance, payout or a completed review from an unfinished assessment.

## Routine three-bullet introduction

For multi-item news, X and blog bounties, the introductory Text block contains **only three short bullets**, in this order:

1. **Accepted:** start with the exact count of unique accepted stories/items, then “recommended for acceptance:” and a brief specific rundown using recognizable short titles/event descriptions. For example: “2 stories recommended for acceptance: Atlas launches a wallet; Council adopts staking rules. 1 still needs correction.” Use stories for news and items for other work. Count items, not proposals or findings. Generic categories such as “the qualifying launches and governance proposals listed in Geo” are insufficient. An accepted event can still require metadata/content repairs; say so without reducing its acceptance count. Keep confirmed voting/publication wording separate, and use it only with current verified receipts. Acceptance never proves approval or payment. Apply this count-first Accepted wording to non-routine Geo reports too.
2. **Rejection:** identify the work that failed and briefly explain why. Before voting, say “recommended for rejection”; after a verified NO vote, say “NO votes recorded.” Do not imply final governance closure from a NO vote alone.
3. **Feedback:** briefly remind the curator of the relevant requirements/checks in plain language, so the question has context. Then ask one kind, neutral question about how the verified issues slipped through their checks. State useful corrections, ask them to check all similar eligible issues in this submission and strengthen those checks to prevent recurrence. Include “Open each finding for details” within this bullet when findings exist.

Approved style example for a Crypto news batch: “The bounty asks you to check for earlier Geo coverage, direct Crypto relevance, and accurate dates and wording. Could you explain how these issues slipped through your checks? Please correct the date and wording issues in the accepted stories, check for similar errors throughout the submission, and strengthen your checks to prevent these issues in future work. Open each finding for details.” Adapt the requirements, space and corrections to the actual review; do not copy Crypto/news criteria into other bounties. Attribute a check to the bounty only when supported by its specification or the editor’s established requirements. For a task without a bounty, refer to the agreed task requirements. Ask to understand the process, without assuming carelessness or promising that mistakes can never recur. Keep this to a few short sentences; the findings carry each error’s explanation and prevention check.

Keep it quick to scan. Use short names or a clearly linked group for large batches; retain the complete item mapping privately. Put full reasons, each distinct error-type question, original statements and sources in the findings/table. The acceptance count is public. Keep scoring, points, cap checks and execution controls private. The page name and recorded metadata carry the bounty/date; do not add extra Text paragraphs for them. Do not append a “Review feedback” heading, separate table-opening instruction, status disclaimer or proposal inventory to this Text block. The native table keeps its own title.

Request current repairs only for eligible work or where a correction could change eligibility. For an independently rejected duplicate or out-of-scope item, ask about the checking process and explain prevention; do not tell the curator to repair it. If there are no issues, state that plainly without inventing a question or correction. Empty acceptance groups say “0 stories/items recommended for acceptance”; empty rejection groups say “None”. Missing material decisions remain private investigations, not a final three-bullet report.

Record concise copy as `review.recipientSummary: {acceptance, rejection, feedback}`, with one nonempty paragraph per field and no bullet prefixes. `reportDraft` exposes `introductionLayout: "routine-three-bullets-v1"` and `introduction`; use that exact introduction in manual update packages too. The Geo builder emits it without extra text and keeps the complete native table/finding pages. The Accepted rundown is always derived from scoped item decisions; legacy `acceptance` prose is preserved in the stored review/hash but no longer overrides it. Supply short, specific `coverage[].recipientName` / `itemName` values, not generic category labels. Large batches preview a few names and say exactly how many more; Notion retains every title/link in its lists. The agent must still write brief rejection reasons and specific useful corrections. Existing verified reports/history are not automatically republished because the renderer changed.

## Full findings and delivery verification

The recipient report has the six agreed comparison fields and full text. Show every distinct verified error type with one example; include its neutral process question, useful correction and prevention check in Issue using `findingIssue`. Do not omit these fields in manual update packages. There is no five-finding cap. Keep internal coverage/requirement notes in the case JSON; do not append them beneath the recipient table. Native tables may show a mandatory Name column or shortened previews; complete finding pages/blocks must expose the full original, exact excerpt and supporting evidence. Keep full per-item outcomes and unresolved checks in the internal case record. Recipient feedback may identify which items passed or failed and what needs correcting, with the accepted item count, without exposing scoring or points. Pending submissions link to real governance proposals and captured values; never invent a live entity page.

Prepare publication ops through geo-publish and use the recorded report authorization. If that authorization is absent or the operation falls outside it, show the concrete report package before requesting the missing approval. Report authorization does not authorize curator votes, proposal execution, awards or messages. Store submitted report proposal IDs separately from indexed report IDs and verification receipts. Before broadcasting, persist the exact publication intent and an unknown delivery receipt. After an unknown write outcome, inspect proposal/report state before retrying. The runner keeps submitted/unknown/failed deliveries out of fresh-create drafts, including across case revisions. Use the explicit reconciliation transitions in routine.md; missing indexed content alone never proves that broadcasting failed. Reuse the existing case mapping and verify every changed field, proposal references and evidence after indexing. Mark delivery verified only on successful readback; failures retain the prior receipt and exact retry blocker.

The review runner produces drafts only. `scripts/report-ops.mjs DRAFT_JSON DELIVERY_PLAN_JSON OUT_JSON` can build a create-only GRC-20 dry-run package using the installed geo-publish SDK (`GEO_CM_DIR`). It cannot sign/upload/broadcast. Supply current discovery, duplicate/schema receipts, exact item/proposal and citation target identities; reuse the existing Review finding model after inspecting its schema. The Crypto pilot explicitly proposes adding the existing Issue property to that type in the datasets perspective. Native tables have mandatory Name/previews; complete finding blocks retain all six fields. A captured pending citation target is a proposed-content reference, not an indexed page; preserve its direct source/proposal URL. Updates require a live preservation/merge plan through geo-publish; the create helper deliberately refuses them. An agent must complete the geo-publish authorization and readback workflow for delivery. Supervised Crypto publication/readback has succeeded; this does not prove unattended scheduling or general preservation updates. Keep those acceptance gates separate from the agent’s default report-delivery obligation.

Keep the editor-only selection/points summary in a separate local/internal artifact. Do not place it in a shared report, finding page, table, Notion body or curator message; hiding it in a collapsed block is not sufficient. Publish only the recipient Markdown/findings, not the internal review JSON.

Before final report delivery, require `reviewReadiness(case).complete`. An unresolved material submission decision stays in the investigation queue; it cannot be published as a final review. The operation helper checks this independently of draft labels.

After verified publication, record the dated feedback snapshot in the configured Notion history log and verify it under [review-history.md](review-history.md). Geo remains the primary feedback destination; a log failure leaves a separate pending task without reopening successful publication. Then generate linked curator feedback and present the editor vote plan as described in SKILL.md. Publication failure must not stop useful feedback preparation, but the draft must clearly retain its missing-link blocker.
